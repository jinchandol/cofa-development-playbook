# CONTRACT

근거/버전: <원본 README·데이터·인터뷰 경로/시점>. 과제 README의 문서명·경로·양식·추가 파일 제한을 우선한다. 이 기본 양식은 미지정 범위에서 필요한 부분만 사용한다.
상태: 명시 / 현업 확정 / 개발 판단 / 가정 / 미확정. 미확정은 확정 근거 없이 바꾸지 않는다.

- 성공 기준·측정식/목표·출처: <내용> · 필수/개선 목표/범위 밖: <내용/이유>

## Data Contract — 분석 6단계

해당 파일/관계에 필요한 검사만 수행하고 원본을 보존한다. 파일명·열·키/행·집계식·건수·사례를 근거로 남긴다.

| 순서 | 검사/해석 | 기록할 결과 |
|---|---|---|
| 1. 파일/스키마 | 파일 목록·인코딩·행 수·열·타입/단위·결측·중복·이상값 | 실제 수치/표본, 읽기 실패·필수값 문제 |
| 2. 관측 단위/키 | 한 행이 엔터티/사건/이력 중 무엇인지, 식별키·복합키의 유일성/충돌 | 검증한 키 후보와 반례, 확정/추정 |
| 3. 관계/변환 | 파일 간1:1/1:N/N:M·참조 무결성·공유/반복·조인 전후 행 수/증폭/손실 | 참조 오류·미매칭·입력=수용+중복제거+격리 등 수지 |
| 4. 업무 의미 | 같은 ID/대상·순서·상태·단위가 업무에서 무엇을 뜻하는지 가능한 해석 비교 | 관찰→해석 A/B→결과 차이. 데이터만으로 정책 확정 금지 |
| 5. 질문/확정 | 기술 오류/업무 미확정/개발 판단 구분, 구현을 바꾸는 모호성 질의 | 실제 행/경계 사례·답변 출처·미응답·Golden Case |
| 6. 요구로 연결 | README·데이터 의미·인터뷰를 합쳐 동작/제약/처리 정책/제외 사유 결정 | 요구 ID·완료 조건·검증 방법과 연결, 원본 불변 확인 |

| 파일/관계 | 관측 단위·키·다중성 | 관찰값/근거 | 업무 해석·확정 상태 | 처리 정책·수지 | 요구/테스트 |
|---|---|---|---|---|---|
| | | | | | |

## Business Contract / 인터뷰

| Q/B ID | 파일·키/행·관찰 | 해석 A/B·결과 차이 | 구체적인 질문/정답 사례 | 답변 원문/요약·출처 | 확정/미응답 | 요구/AC 영향 |
|---|---|---|---|---|---|---|
| | | | | | | |

질문은 영향·불확실성·변경 비용 순으로 선별한다. 답이 추상적이면 실제 행/경계 사례로 좁혀 재질의한다.
실제 인터뷰를 하지 않았으면 답변을 지어내지 않는다. 모순되는 README/데이터/답변은 근거를 제시해 확인한다.

|---|---|---|---|---|---|---|---|
| R-01 | | | | | | | |

세 칸 모두에 억지로 출처를 만들지 않는다. 해당없음은 이유를, 모르는 것은 미확정을 표시한다.
원자료의 중요한 항목은 요구/처리 정책/범위 밖 사유로 연결하고 근거 없는 기능은 추가하지 않는다.

## Acceptance Criteria

| AC·요구 ID | 입력/전제 | 행동/조건 | 기대 결과·통과/실패 판정 | 정상·경계·예외/불변 조건 | 테스트/직접 확인 방법 |
|---|---|---|---|---|---|
| AC-01 / R-01 | | | | | |

숫자가 필요한 지표는 단위·분모·기준값을 명시한다. 행위/결과는 예/아니오로 판정 가능하게 쓴다. 임의의 성능 목표를 만들지 않는다.
위반0건만으로 성공이라 하지 않고 검사 대상·최소 유효 출력도 확인한다. 핵심 AC의 입력·기대값은 구현 전에 정한다.
