# CONTRACT — 개발할 내용과 완료 기준

근거/버전: <원본 README·데이터·인터뷰 경로/시점>. 과제 README의 문서명·경로·양식·추가 파일 제한을 우선한다. 이 기본 양식은 미지정 범위에서 필요한 부분만 사용한다.

이 문서는 개발할 동작·처리 규칙과 완료를 판단할 조건을 정한다. 선택 이유·구현 위치·실제 실행 결과는 DECISIONS에 기록한다.
연결에 쓰는 ID: D=데이터 관찰, Q=현업 질문, R=요구사항, AC=완료 조건. 예: D-01 → Q-01 → R-01 → AC-01. 질문이 필요 없는 요구는 Q 없이 연결한다.
아래 표는 필요한 행만 작성한다. 해당 없는 항목은 이유를 적고, 확인하지 못한 내용은 미확인으로 남긴다.

## 목표와 범위

- 사용자·사용 순간·결정할 일: <근거> · 현재 불편/기준값: <관찰 또는 미확인>
- 성공 기준·측정식/목표·출처: <내용> · 필수/개선 목표/범위 밖: <내용/이유>
- 운영 제약: <공식 근거·허용 도구·실행/제출 조건 중 과제에 필요한 것만>

## 데이터 분석 — 필요한 검사 6단계

6단계는 검사 순서이며, 모든 검사 결과를 장문으로 옮길 필요는 없다. 과제에 필요한 검사를 수행하고 요구에 영향을 주는 결과만 아래 D 표에 요약한다. 원본은 보존한다.

| 순서 | 검사/해석 | 기록할 결과 |
|---|---|---|
| 1. 파일과 값 | 파일 목록·인코딩·행 수·열·자료형/단위·빈 값·중복·이상값 후보 | 실제 수치/표본, 읽기 실패·확인이 필요한 값 |
| 2. 한 행의 의미와 식별자 | 한 행이 대상/사건/이력 중 무엇인지, 단일 열 또는 열 조합으로 행을 구분할 수 있는지 | 확인한 식별자 후보·중복 사례, 관찰 사실과 의미 추정의 구분 |
| 3. 파일 간 연결과 변환 | 어떤 열로 연결되는지, 양쪽 기준으로 한 건에 한 건/여러 건이 연결되는지, 연결되지 않는 값·공유/반복·결합 전후 건수 | 빠지거나 늘어난 건수와 이유, 원본과 결과를 대조할 방법 |
| 4. 업무 의미 | 같은 ID/대상·순서·상태·단위가 업무에서 무엇을 뜻하는지 가능한 해석 비교 | 관찰 → 해석 A/B → 출력/동작 차이. 반복 행이나 미연결 값이 곧 업무 오류라고 단정하지 않음 |
| 5. 질문/확정 | 자료만으로 결정할 수 없고 구현을 바꾸는 업무 규칙을 구체적으로 질의 | 실제 행/경계 사례·실제 답변 출처·미응답, 담당자가 확인한 입력과 기대 결과 사례 |
| 6. 요구로 연결 | README·데이터 의미·인터뷰를 합쳐 동작/제약/처리 정책/제외 사유 결정 | 요구 ID·완료 조건·검증 방법과 연결, 원본 불변 확인 |

| 분석 ID·대상 | 한 행의 의미·식별자·연결 관계 | 확인한 사실·근거 | 업무 해석·확인할 점 | 영향받는 요구 ID |
|---|---|---|---|---|
| D-01 / `<파일·열/관계>` | `<행의 의미·연결 방식>` | `<건수·키/행·분석 명령/결과 위치>` | `<관찰과 추정 구분·필요 시 Q ID>` | `<R ID/범위 밖 사유>` |

데이터에서 확인한 사실과 업무 해석을 구분한다. 채택할 중복 처리·누락 처리 등은 근거를 확인한 뒤 요구사항에 적고, 실제 변환 전후 건수는 DECISIONS의 실행 증거에 남긴다. 중복 제거·격리를 기본 정책으로 가정하지 않는다.

## 현업 인터뷰 — 구체적인 질문과 실제 답변

| 질문 ID | 질문 근거 | 구체적인 질문·해석별 결과 차이 | 실제 답변·출처 | 답변 상태 | 영향받는 요구 ID |
|---|---|---|---|---|---|
| Q-01 | `<D ID 또는 README 위치·관찰>` | `<실제 사례·선택지·기대 결과 확인>` | `<원문/요약·응답 위치/시점 또는 미응답>` | `<미질의/답변 대기/재질의 필요/해결>` | `<R ID>` |

질문은 영향·불확실성·변경 비용 순으로 선별한다. 답이 추상적이면 실제 행/경계 사례로 좁혀 재질의한다.
실제 인터뷰를 하지 않았으면 답변을 지어내지 않는다. 모순되는 README/데이터/답변은 근거를 제시해 확인하고, 답변을 받았더라도 쟁점이 남으면 해결로 쓰지 않는다.

## 요구사항 — README·데이터·인터뷰 종합

| 요구 ID | 개발할 동작·처리 규칙/필수·개선 | README 근거 | 데이터 근거 | 인터뷰 근거 | 확정 상태 | 완료 조건 ID |
|---|---|---|---|---|---|---|
| R-01 | `<누가/어떤 상황에서 무엇을 할 수 있는지·필수/개선>` | `<절/행 또는 해당 없음과 이유>` | `<D ID/해당 없음과 이유>` | `<Q ID/해당 없음과 이유>` | `<확정/가정/미확정>` | AC-01 |

세 출처를 검토하되 개별 요구마다 세 칸 모두에 억지로 근거를 만들지 않는다. 원자료 위치는 직접 적거나 D/Q 기록을 참조한다.
확정 상태는 출처 종류가 아니라 요구의 결정 상태다.

- 확정: README·실제 답변 등 유효한 근거로 동작/규칙을 정했고 중요한 충돌이 해소됨.
- 가정: 답이 없는 부분을 임시로 정한 상태. 가정 내용·영향·확인할 질문을 연결하고, 확정 답변처럼 취급하지 않음.
- 미확정: 동작 또는 판정 기준을 아직 정하지 못함. 영향을 받는 구현 범위를 명시함.

기술적 선택의 이유는 DECISIONS에 기록하며, 개발 편의를 현업 답변의 근거로 사용하지 않는다. 미확정을 근거 없이 확정으로 바꾸지 않는다.
원자료의 중요한 항목은 요구/처리 정책/범위 밖 사유로 연결하고 근거 없는 기능은 추가하지 않는다.

## 완료 조건 — AC

| 완료 조건·요구 ID | 입력·사전 조건 | 실행할 동작 | 기대 결과·판정 기준 | 기대값 근거 | 확인 방법 |
|---|---|---|---|---|---|
| AC-01 / R-01 | `<구체적인 입력/초기 상태>` | `<사용자 동작/처리>` | `<출력 값/상태·통과와 실패의 기준>` | `<README 위치·Q ID·원본의 별도 계산 등>` | `<테스트/명령/화면·대조 방법>` |

한 행은 독립적으로 통과/실패를 판단할 조건 하나다. 정상·경계·예외 중 요구에 필요한 사례를 고르고, 항상 유지해야 할 규칙도 입력 범위와 판정식을 정한다.
숫자가 필요한 지표는 단위·분모·기준값을 명시한다. 행위/결과는 예/아니오로 판정 가능하게 쓴다. 임의의 성능 목표를 만들지 않는다.
핵심 AC의 입력·기대값은 구현 전에 정하고, 구현의 실제 출력을 그대로 정답으로 삼지 않는다. 0건이 정상인 사례와 출력 누락을 구분하도록 검사 대상·예상 건수도 적는다.
요구사항 표는 AC ID만 참조하고 상세 조건은 이 표에 한 번만 적는다. 확인 방법은 검증 계획이며 실제 실행 결과·통과 여부는 DECISIONS에 기록한다.
