# 초기 분석 기록

범위: README R-01~07, data/ 3파일. 작성자가 정답 생성에도 관여한 비블라인드 리허설이다.
프로파일링 명령: `python profile_data.py` (종료 0). 원시 결과는 evidence.json의 raw_profile에 저장한다.

| 파일 | 행 의미 | 수 | 후보 키/관찰 |
|---|---|---|---|
| routes | 노선 마스터 레코드 | 5 | route_id R3 충돌, 문자열 name, active boolean-text |
| stops | 정류장 마스터 레코드 | 6 | stop_id S3 완전중복, S5 이름 결측 |
| route_stops | 노선 내 경유 사건 후보 | 16 | (route_id, sequence) 중복. (route_id, stop_id)는 순환 때문에 키 불가 |

관계: route → 경유 1:N, stop → 경유 1:N, route ↔ stop N:M.
원시 inner join은 16→18행. 참조 없는 경유 3행이 소실되면서 중복 키가 행을 증폭하므로 결과 행 수만으로 무결성을 판단하면 안 된다.
raw 참조 검사는 S5의 이름 결측과 R3의 충돌을 잡지 못한다. 정제된 마스터를 만든 뒤 참조를 재검사해야 한다.

## 관계에서 업무 의미로 연결한 예

아래 해석은 처음부터 확정된 사실이 아니라 질문으로 구분해야 하는 가설이다. 답변은 INTERVIEW.md의 합성 Q/B 기록을 사용한다.

| 데이터 관찰 | 가능한 업무 의미 | 해석에 따른 결과 차이 | 질의→확정→요구 |
|---|---|---|---|
| R1의 다른 순번1/3에 S1이 반복 | 중복 추출 또는 실제 재방문 | 정류장ID로 접으면 유효3건, 경유 사건이면4건 | Q1→B-01 재방문 유지→R-03/AC-03 |
| S3를 R1/R2/R4가 공유, R4는 운휴 | 정상 공유, 운행 노선만 조회, 오류 경유 포함 등 | 역조회 대상에 R4/R2를 넣는지 달라짐 | Q5/Q3→B-02/04 운휴 포함·blocked 제외→R-04 |
| R3의 같은 ID에 서로 다른 이름 | 버전 이력, 추출 오류, 덮어쓰기 대상 등 | 마지막행 선택 또는 ID 전체 격리로 목록이 달라짐 | Q2→B-03 전체 격리→R-01/02/06 |
| R2의 같은 순번2에 다른 정류장 | 대체 경로/버전 또는 순서 오류 | 승자 하나를 고르거나 전체 경유를 차단 | Q3→B-04 전체 경유 격리→R-03/06 |

원본만으로 각 가설의 정답을 정하지 않는다. 키/관계 검사 결과를 업무 질문으로 연결하고, 답변이 바꾼 요구/완료 조건을 CONTRACT에서 추적한다.

## 분류

- 기술적 관찰: 중복 키, 결측, 존재하지 않는 참조, 순번 0/빈값. 오류의 존재는 재현 가능하나 처리 정책은 업무 확인 대상.
- 업무 미확정: R1 S1 재방문, R2 동일 순번 충돌, R3 충돌 식별자, 공유 정류장/운휴 노선 역조회, 결측 행 부분 제외 여부.
- README 명시 제약: 원본 불변(R-01/R-05). 개발자가 임의로 선택하거나 완화할 수 있는 정책이 아니다.
- 개발 판단: 표준 라이브러리 HTTP/JSON, 파생 상태 파일, 단일 프로세스 잠금·원자 교체, UI textContent.

새 리허설에서는 최소 계약에 대해 요구사항 리뷰를 수행한 뒤 목록→상세→편집 저장→품질 보고 순서로 구현한다. 질문을 무한 확장하지 않는다.
초기 리허설의 개발 전 요구사항 리뷰 이력은 없으며, 이번 문서 감사에서 기존 요구를 소급 대조했다. 이를 과거에 수행한 리뷰로 주장하지 않는다.
초기 프로파일의 키 존재 검사만으로 관계가 안전하다고 판단하는 결함을 발견하여, 정제 마스터 참조 검사와 행별 수지를 계약에 추가했다.
